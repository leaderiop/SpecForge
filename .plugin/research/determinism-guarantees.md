# Determinism Guarantees per Plugin Runtime — Research (R-6)

**Scope:** Can each candidate runtime guarantee *same input + same code = same output* across (a) runs, (b) platforms, (c) versions? What mechanism enforces it, and who relies on it in production? Companion to `../dimensions/D09-determinism-formal.md` (which covers the host-side contract); this file is the per-runtime, source-verified deep dive.

**Method:** Every load-bearing claim below was verified against a primary source in this session (spec text, engine source, API docs, or protocol CAP). Sources listed inline; the two exceptions are flagged.

---

## 1. WASM — the only candidate with a *spec-level* determinism story

### 1.1 The spec now defines a deterministic profile

WebAssembly 3.0 (2026) added **Profiles** to the core spec. The **deterministic profile (DET)** "defines a sub-language that does not exhibit any incidental non-deterministic behaviour":

- "All NaN values generated by floating-point instructions are canonical and positive."
- "All relaxed vector instructions have a fixed behaviour that does not depend on the implementation."

Caveat stated in the same appendix: `memory.grow` / `table.grow` "technically remain non-deterministic … in order to be able to indicate resource exhaustion" — i.e. a plugin that allocates unboundedly can trap at input-dependent points unless the host bounds memory. Source: [Wasm 3.0 spec, Appendix — Profiles](https://webassembly.github.io/spec/core/appendix/profiles.html).

Core wasm semantics outside those corners are deterministic: fixed-width IEEE-754 ops, no ambient clock/RNG/fs in the core instruction set — nondeterminism enters only via (1) NaN payloads, (2) relaxed SIMD, (3) threads/atomics, (4) **host imports**. Category (4) is the one under host control (import allowlist ⇒ purity), which is exactly C7-04's fs-allow-by-default hole in SpecForge today.

### 1.2 Engine knobs (wasmtime 49, verified in Config docs)

| Knob | Default | Determinism role |
| --- | --- | --- |
| `Config::consume_fuel(true)` + `Store::set_fuel` | off | Docs: "This can be used to **deterministically prevent** infinitely-executing WebAssembly code" — an instruction-count budget, machine-independent ([docs.rs/wasmtime Config](https://docs.rs/wasmtime/latest/wasmtime/struct.Config.html)) |
| `Config::epoch_interruption` | off | Cheap wall-clock timeslicing — correct for watch-mode timeouts, **wrong** for reproducible truncation (kills divergent passes at different points per machine) |
| `Config::wasm_relaxed_simd` | **true** | Relaxed SIMD ops "are allowed to produce different results on different platforms" — wasmtime's docs cite x86_64 vs AArch64 divergence |
| `Config::relaxed_simd_deterministic` | false | Forces spec-classified deterministic behavior across all platforms at a perf cost |
| `Config::cranelift_nan_canonicalization` | false | Canonicalizes NaN payloads — removes cross-platform NaN divergence |
| `Config::wasm_threads` | on (recent) | Threads/shared memory are nondeterministic *if used*; a deterministic host should disable outright |

Two strong signals that this bundle is the industry-standard recipe:

- wasmtime's own **record/replay** mode (`Config::rr`) refuses to validate unless determinism settings are correct: "validation fails if settings that control determinism are not set appropriately. In particular: Enabling NaN canonicalization …; Enabling deterministic relaxed SIMD" (same Config docs). Execution-trace reproducibility is a shipped feature, not an aspiration.
- **Extism already exposes fuel end-to-end**: `options.fuel` / `options.initialization_fuel` → `config.consume_fuel(true)` → `store.set_fuel(...)` per call, with `fuel_consumed()` reporting and an explicit `"plugin ran out of fuel"` error path (verified in extism `runtime/src/plugin.rs`, main branch). It also sets `epoch_interruption(true)` for the manifest's `timeout_ms`. **Implication for the audit:** C7-10 (`max_execution_ms` unused) has a first-party fix that is *deterministic* — set `PluginBuilder::fuel`, don't invent a wall-clock timeout.

### 1.3 Guarantee verdict for wasm

- **Across runs:** yes — fresh instances, no shared state; host imports allowlisted ⇒ bit-identical.
- **Across platforms:** yes for integer code unconditionally; for float/SIMD code under the DET-profile config (NaN canonicalization + deterministic relaxed SIMD or SIMD rejection). SpecForge's builtin passes are integer-only, but a third-party plugin can emit floats, so the config must be pinned, not hoped for.
- **Across versions:** the wasm spec is stable and conformance-tested; a validated module's *semantics* don't drift. What does drift across wasmtime versions: fuel **cost tables** (same budget, different exhaustion points across engine versions) and trap message text. Pin the engine version for byte-identical fuel semantics; outputs stay identical regardless for non-exhausting runs.

**Best-in-class.** No other candidate has determinism as a machine-checkable property of the runtime contract rather than a coding convention.

## 2. Lua — deterministic *only if the host re-implements what Redis built*

### 2.1 Hash/iteration order is randomized per state — in both implementations

The dimension doc D09 asserts "Lua 5.4 unseeded string hashes; LuaJIT deterministic." **Both halves are wrong at the source level:**

- **PUC Lua 5.4** (`lstate.c`, tag v5.4.7): `luai_makeseed` — "A macro to create a 'random' seed when a state is created; the seed is used to randomize string hashes" — seeds from `time(NULL)` **plus heap addresses** (ASLR). Every fresh `lua_State` shuffles `pairs()` order by default. Override requires compile-time `LUAI_MAKeseed` (or, in Lua 5.5-dev, the new explicit `lua_newstate(f, ud, seed)` parameter).
- **LuaJIT 2.1** (`lj_str.c`): `g->str.seed = lj_prng_u64(&g->prng)` at state init, plus `LUAJIT_SECURITY_STRHASH` keyed sparse/dense ARX re-hashing on collisions. Randomized per state, same conclusion.

So a Lua plugin that iterates a table to emit findings has the *exact bug class* SpecForge's formal guest already has with Rust `HashMap` — except in Lua it re-randomizes on every fresh VM, per run. `table.sort` before output is a convention, and conventions are what AI-authored plugins will forget.

### 2.2 The step limit: real but order-sensitive

- `debug.sethook(f, mask, count)`: "the count hook: is called after the interpreter executes every `count` instructions" ([Lua 5.4 manual §6.2/§debug.sethook](https://www.lua.org/manual/5.4/manual.html)). VM-instruction counts are machine-independent — same build, same script, same order ⇒ same count.
- mlua wraps this directly: `Lua::set_hook(HookTriggers { .. })` — docs: "This can be used to implement a limited form of execution limits by setting `HookTriggers.every_nth_instruction` and erroring once an instruction limit has been reached" ([docs.rs/mlua](https://docs.rs/mlua/latest/mlua/struct.Lua.html)). Luau replaces hooks with `set_interrupt` (VM instruction counter — same class, mlua docs: "continuous execution limits by instructing Luau VM").

But instruction totals are a function of **iteration order** (which code path runs), and §2.1 says order is seeded. A Lua fuel budget is therefore only fully deterministic *after* you fix the hash seed — the step limit inherits the seeding problem.

### 2.3 GC: controllable, mostly irrelevant to output

mlua exposes `gc_stop` / `gc_restart` / `gc_collect` / `gc_step` — the host can force full collections and even stop the GC during a plugin call. Output only leaks via `__gc` finalizers with side effects; `collectgarbage("collect")` before reading results neutralizes it. GC is a minor hazard here, unlike Python where finalizers/timing interleave with everything.

### 2.4 Guarantee verdict for Lua

- **Across runs:** no, by default — string-hash seeding (PUC and LuaJIT) re-shuffles `pairs()` per state; needs a custom interpreter build (fixed seed) or discipline (sort everything).
- **Across platforms:** mostly — Lua is plain C, `%".14g"` float formatting is fixed in `luaconf.h` (`LUA_NUMBER_FMT "%.14g"`); endianness/word-size differences are the classic porting risk (Redis had to guarantee its embedded PRNG across "32-bit, 64-bit, big-endian and little-endian systems", see §2.5).
- **Across versions:** the manual leaves `pairs()` order *unspecified* and `#` borders implementation-defined; 5.1→5.4 changed float/integer semantics and tostring details. Interpreter-version pinning is mandatory for reproducibility.

**Key existence proof — Redis** (archived official docs, *Programmability/EVAL-intro*): Redis shipped deterministic Lua scripting for a decade because *replication* required "the script always must execute the same Redis write commands with the same arguments given the same input data set … Nor can it depend on any external input from I/O devices." Enforcement was **host-side and mechanical**: no `os`/time exports to scripts; error on write-after-nondeterministic-command; a "silent lexicographical sorting filter" on `SMEMBERS` etc. before results enter Lua (4.0); `math.random` patched to a fixed seed whose output "is guaranteed to have the same output regardless of the architecture of the system"; and the seed-propagation pattern (pass the PRNG seed as a script argument, replicate it) for scripts that genuinely need randomness. When Redis 5.0 moved to effects replication, the determinism requirement was dropped *because the architecture changed* — an honest lesson: host canonicalization can substitute for script purity ([archived docs](https://web.archive.org/web/2022id_/https://redis.io/docs/manual/programmability/eval-intro/)). Note the lexicographic-sorting precedent: that is precisely the "host canonicalizes at the boundary" fix D09 recommends for `analyze.rs`.

## 3. Python — no mechanical determinism exists, only environment scrubbing

- **`sys.deterministic` does not exist.** Neither does any `PYTHONDETERMINISTIC` env var — verified against the full CPython command-line/environment reference ([docs.python.org/3/using/cmdline.html](https://docs.python.org/3/using/cmdline.html)). The assignment's "sys.deterministic?" resolves to: not a thing.
- **`PYTHONHASHSEED`** is the entire built-in story: fixed integer seed ⇒ repeatable `hash()` for str/bytes, so set/dict *iteration* stabilizes. Docs frame its purpose as "to allow repeatable hashing, such as for selftests for the interpreter" — a test harness feature, not a sandboxing contract. It also doesn't touch float formatting, `os`, `time`, sockets, or `locale`.
- Everything else leaks by design: ambient fs/net/process are one `import` away; GC pauses and `__del__` timing are real; error **message text** changes across 3.x minors (snapshot tests break on interpreter upgrade); `locale`-dependent formatting exists. A PyO3 host can pin `PYTHONHASHSEED=0`, deny-list modules at import hooks, and chroot the process — but every layer is advisory against a language whose standard library is *defined* as an ambient-capability surface.
- **Guarantee:** runs — only with scrubbed env; platforms — byte-level no (hash of types beyond str/bytes, C-extension variance); versions — no (language + stdlib + error text drift). **No production system uses embedded CPython as a determinism contract; reproducible-builds practice stops at `PYTHONHASHSEED=0` for *build* reproducibility.**

## 4. JavaScript/V8 — deterministic *flags exist*, but they're a testing mode, not an embedding contract

### 4.1 V8 (what `deno_core` embeds)

Verified in V8's `flag-definitions.h`:

- `--predictable` ("enable predictable mode"): forces `single_threaded_gc`, disables concurrent recompilation, background compile tasks, memory reducer — and **`DEFINE_VALUE_IMPLICATION(predictable && random_seed == 0, random_seed, 12347)`** — predictable mode pins `Math.random` to seed 12347 unless overridden.
- `--random-seed=N` — "Default seed for initializing random generator (0 … means to use system random)".
- `--hash-seed=N` — "Fixed seed to use to hash property keys (0 means random) … **with snapshots this option cannot override the baked-in seed**" — a real caveat: snapshot-based embedders can't fully re-seed key hashing.
- `--predictable_gc_schedule` — "Fixes heap growing, idle, and memory reducing behavior"; `--verify_predictable` exists to *check* predictability.

The good structural news: ES2015+ **spec-mandates** iteration order — integer-like keys ascending, string keys insertion order, `Map`/`Set` insertion order. V8 is the only interpreter tier where *the language itself* forbids the HashMap-iteration bug class. The bad news: `--predictable` is documented and used as a **fuzzing/regression mode** (single-threaded, slower, disables optimizations' concurrency) — embedding it in a production host via deno_core is possible but off the supported path, and cross-*version* drift (error messages, ICU/`Intl` data, `Date`/locale formatting) remains unbounded.

### 4.2 QuickJS — smaller, but `Math.random` is time-seeded by default

`quickjs.c`: `ctx->random_state = ((int64_t)tv.tv_sec * 1000000) + tv.tv_usec;` — seeded from `gettimeofday` per context; no public re-seed API found in either bellard/quickjs or quickjs-ng headers. So QuickJS is *not* deterministic across runs out of the box; it requires a source patch (small, but it's your fork). Step limiting exists and is clean: `JS_SetInterruptHandler` + an internal `interrupt_counter` ("when the counter reaches zero, JSRuntime.interrupt_handler is called", reset to `JS_INTERRUPT_COUNTER_INIT` on entry) — instruction/callback-granular, same order-sensitivity caveat as Lua.

**Guarantee for the JS tier:** runs — yes *with* `--predictable`/seed flags (V8) or a patched QuickJS; platforms — iteration order is spec-fixed, so structural output is stable; float `toString` is spec-pinned shortest-round-trip; but `Intl`/ICU data is platform-bundled in V8; versions — engine-version pinning required (message text, flag semantics drift). "Deterministic V8" is a tested, real configuration — V8's own CI depends on it — but it is the *least* contract-like of the wasm-grade mechanisms.

## 5. The gold standard: languages with determinism in the *spec*

**Starlark** (the Bazel build language — a Python dialect embedded in a build tool, i.e. structurally SpecForge's exact niche):

> "Starlark execution is *deterministic*: all functions and operators in the core language produce the same execution each time the program is run; **there are no sources of random numbers, clocks, or unspecified iterators**. This makes Starlark suitable for use in applications where reproducibility is paramount, such as build tools." ([starlark-go spec](https://github.com/google/starlark-go/blob/master/doc/spec.md), Overview)

This is the property the interpreter tier *cannot* retro-fit: determinism achieved by removing nondeterministic primitives from the language, not by configuring the engine. ## 7. Cross-cutting findings

1. **All step budgets are iteration-order-sensitive.** Fuel (wasmtime), instruction hooks (Lua/`every_nth_instruction`), and interrupt counters (QuickJS) count *executed steps*; if hash-seeded container order varies, the step total and even the truncated-finding set vary with it. Seeding is the root toggle; budgets are only deterministic on top of fixed order. This unifies every runtime above.
2. **The deterministic recipe is runtime-independent and known**: (a) allowlist imports/std libs to pure functions; (b) fix all seeds; (c) meter with instruction counts, never wall-clock; (d) canonicalize output order at the host boundary. Wasm is merely the only candidate where (a) is *structural* (no ambient imports exist to allow by accident) and (b) is unnecessary (no hash-order leakage across the ABI) — the recipe degenerates to (c)+(d).
3. **Cross-version is the hard axis for every interpreter.** Wasm pins semantics by spec + conformance suite; engines may only change *cost tables* (fuel) and trap text. Lua/Python/JS change semantics, stdlib behavior, and error message text across minor releases — snapshot tests break with interpreter upgrades. Soroban's answer ("replaying … in an upgraded host environment will produce observably-identical results") is a *pinned-wasm* answer; no interpreter runtime in this comparison makes the equivalent commitment without pinning the exact interpreter build.
4. **The mechanism doesn't have to live in the guest.** Redis sorted `SMEMBERS` before handing results to Lua; D09 recommends sorting findings at `analyze.rs:183-187`. Host canonicalization fixes output *order* for all guests at once; only content divergence (E041's DFS-reach-order message) needs the guest fixed (`BTreeMap`).

## Bottom line

Only wasm offers determinism as a *checked property of the runtime contract* (spec DET profile + wasmtime refuses nondeterministic configs for record/replay + Extism-native fuel). Lua can be made deterministic the way Redis did it — with substantial host machinery (fixed-seed build, sorted iteration, seed propagation) and a pinned interpreter. Python has no mechanical story beyond `PYTHONHASHSEED=0` plus environment scrubbing. JS/V8 has real deterministic flags (`--predictable`, `--hash-seed`, `--random-seed=12347`) but as a fuzzing mode, not an embedding contract, and ES iteration order — while spec-fixed — does nothing about ambient `Math.random`/`Date`/ICU. Production demand for deterministic plugin execution is real and concentrated (blockchain consensus, checkout pricing, hermetic builds) and it has voted overwhelmingly for capability-restricted wasm. Fuel over wall-clock is also the correct fix for SpecForge's C7-10, and it already exists in Extism (`PluginBuilder::fuel` / `initialization_fuel`).

## Verdict

**Verdict:** KEEP_WASM
**Confidence:** 4
**One-line rationale:** Wasm is the only candidate whose determinism is machine-checkable — spec DET profile, engine-validated config bundles, and Extism-native fuel make "pure function of pinned module bytes + input + fuel" enforceable, while Lua/Python/JS can only approximate it with conventions, env scrubbing, or fuzzing-mode flags that no production embedder treats as a contract.
