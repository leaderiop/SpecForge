# Case Study — HashiCorp go-plugin (Packer/Terraform/Vault/Nomad/Boundary/Waypoint)

**Lens (Nygard):** a plugin system is an integration contract bought with operational cost. go-plugin is the industry's longest-running out-of-process experiment: 13+ years in production, "millions of machines" (README), and its evolution — net/rpc → gRPC → AutoMTLS → versioned protocols — is the most complete public record of what a plugin runtime actually costs and what it never solved.

Sources: [go-plugin README](https://github.com/hashicorp/go-plugin/blob/main/README.md) · [go-plugin server.go / client.go](https://github.com/hashicorp/go-plugin/blob/main/client.go) · [non-Go plugin guide](https://github.com/hashicorp/go-plugin/blob/main/docs/guide-plugin-write-non-go.md) · [Terraform plugin protocol](https://github.com/hashicorp/terraform/blob/main/docs/plugin-protocol/README.md) · [Terraform plugin docs](https://developer.hashicorp.com/terraform/plugin/how-terraform-works) · [Terraform debugging](https://developer.hashicorp.com/terraform/plugin/debugging) · [Vault plugin ecosystem](https://developer.hashicorp.com/vault/docs/plugins) · [Vagrant plugins](https://developer.hashicorp.com/vagrant/docs/plugins) · [Waypoint plugins](https://github.com/hashicorp/waypoint/blob/main/website/content/docs/plugins.mdx)

## 1. How go-plugin works

**Model: host is the client, plugin is the server.** The host spawns the plugin as a child process. The plugin binds a listener (Unix domain socket, or localhost TCP on Windows), prints exactly one handshake line to stdout — `CORE-PROTOCOL-VERSION|APP-PROTOCOL-VERSION|NETWORK-TYPE|NETWORK-ADDR|PROTOCOL`, e.g. `1|1|unix|/tmp/plugin123|grpc` — and the host dials it (server.go; non-Go guide). Core protocol version has sat at `1` for the system's whole life; any mismatch is rejected with a human-friendly error.

- **Handshake gating:** before the line, the child must see a magic-cookie env var (`MagicCookieKey`/`MagicCookieValue` in `HandshakeConfig`). The source is explicit: *"This is not a security measure, just a UX feature"* — its only job is friendly errors when a plugin binary is run by a user directly (server.go:50-62).
- **Transport:** one connection; `net/rpc` plugins multiplex over [yamux](https://github.com/hashicorp/yamux), gRPC plugins get HTTP/2 streams for free (README). *"Plugins over a real network are not supported and will lead to unexpected behavior"* — this is a localhost IPC library that happens to speak gRPC.
- **Services:** gRPC plugins must register the standard [gRPC Health Checking Service](https://github.com/grpc/grpc/blob/master/doc/health-checking.md) with `"plugin" = SERVING`, which the host uses for `Ping()`; a plugin without it "may be abruptly restarted" (non-Go guide, step 3).
- **Lifecycle & observability:** host owns the child; kills it on exit. Plugin stdout/stderr are *hijacked and mirrored* to the host (so plugin authors keep using `log`; hclog lines arrive structured), stdin is inherited for TTY pass-through (README). `SecureConfig` verifies a checksum before exec; `AutoMTLS` gives one-time mutual certs generated at spawn — *"the client generates a one-time use tls certificate, sends the public x.509 certificate to the new server, and the server generates a one-time use tls certificate back"*, so only the spawning host can connect and the host refuses any server it didn't spawn (client.go:247-258). **Note: AutoMTLS is optional and incompatible with Reattach.**
- **Debug ergonomics:** `ReattachConfig` lets a host attach to an already-running plugin process — this is how Terraform provider debugging works: run the provider under delve manually, and `TF_REATTACH_PROVIDERS='{"…":{"Protocol":"grpc","Pid":3382870,"Addr":{"Network":"unix","String":"/tmp/plugin713096927"}}}'` points the CLI at it (Terraform debugging docs). There is also a test-mode `ServeConfig` that runs the plugin in-process and emits a reattach config.

## 2. What languages can plugins use

Three eras:

1. **net/rpc + gob (2012–2019):** Go-only by construction — Go stdlib RPC and Go's gob encoding on the wire.
2. **gRPC (opt-in since ~2016; default for Terraform protocol 5, v0.12):** any language that can serve gRPC. The official requirements for a non-Go plugin (non-Go guide): implement the `.proto` service, register the health service, print the handshake line. Terraform's protocol README demonstrates generating Python stubs from `tfplugin5.proto` as the supported path to SDK-building in other languages.
3. **The catch:** the *broker* (bidirectional calls, `io.Reader/Writer` streaming) is not fully cross-language — `GRPCBrokerMultiplex` ships "only … a Go implementation for the server (i.e. plugin) side" (client.go:262-272). Non-Go plugins get request/response gRPC, not the full interface fidelity Go plugins get. In practice every official Terraform provider and Vault external plugin is a Go binary.

**Vagrant is the exception that proves the design:** its plugins are in-process Ruby gems — and Vagrant's core is itself implemented on that plugin API ("most of the core of Vagrant is implemented using plugins" — Vagrant docs, the purest R-1 dogfooding in the company). The cost was well known: gem/bundler dependency conflicts are Vagrant's chronic support burden, and the same process means no crash isolation. go-plugin's README answers why they abandoned that world: RPC "was the only option since Go didn't support dynamic library loading", and even today "dynamic library loading is not acceptable for security reasons" (Vault).

## 3. Limitations (observed, not hypothetical)

- **No sandbox — plugins are trusted.** A plugin process holds the invoking user's full privileges; ambient fs/network/process access is unconditional. The entire trust model is *distribution*: checksums (`SecureConfig`), optional TLS, registry review, signed releases. HashiCorp hardened the channel, never the guest. (Vault's mitigation for hostile tenants is to containerize the plugin — OS isolation bolted on outside the library.)
- **First-party tier creeps back.** Vault ships built-in plugins *in-process* (`+builtin` tags, preregistered, "runs those plugins within the main Vault process") alongside external subprocess plugins — an explicit two-tier trust split, plus a semver plugin catalog with pinning that go-plugin itself never provided (its README "roadmap" has promised semantic versioning for years; hosts like Vault built their own catalogs on top).
- **Process economics.** One OS process per plugin instance; Terraform restarts providers once per graph walk (the debugging doc's caveat that debug mode reuses the process "instead of once per walk" confirms the default). Startup latency, RSS, and IPC serialization are paid per instance; the README concedes shared libraries have "much higher performance" but claims their workloads never needed it — Terraform plugins are I/O-bound API adapters, not CPU-bound graph passes.
- **Fragile control channel.** stdout is protocol surface: a stray `println!` in plugin init corrupts the handshake, which is precisely why go-plugin must hijack and mirror stdout/stderr. Health checking exists because half-dead children were common enough to need detection-and-restart.
- **Contract evolution pain.** One integer `ProtocolVersion` was too coarse; Terraform needed package-per-major (`tfplugin5`/`tfplugin6` gRPC services so one server can speak both), negotiated at handshake, with immutable-after-release `.proto` files and minor-version feature detection (protocol README). This discipline *had to be invented on top of* gRPC; netrpc-era plugins had no such path.
- **Platform seams:** unix sockets have extra config unsupported on Windows (client.go, `UnixSocketConfig`); `AllowedProtocols` defaults to netrpc-only for legacy error-message compatibility — every default in the library is a museum of its own history.

## 4. Why Terraform chose gRPC (and never an embedded interpreter)

The question contains a presupposition worth correcting: Terraform's actual choice was **RPC vs in-process code** — providers were originally compiled into the core binary, then externalized into plugin executables (protocol README: "plugins are normal executable programs"; core is a "statically-compiled binary" that communicates "with plugins over RPC"). Embedded interpreters were never the competitor; the alternatives were (a) compiled-in code, (b) shared libraries/dlopen, (c) subprocess RPC. They picked (c) because:

1. **Crash isolation** — "A panic in a plugin doesn't panic the plugin user" (README). Providers wrap hundreds of flaky cloud SDKs; process death is the cheapest error channel.
2. **Dependency isolation** — each provider pins its own AWS/GCP SDK versions; in one process that is dependency hell, in `dlopen` it is ABI hell, in a subprocess it is a non-issue.
3. **Release decoupling** — providers ship on their own cadence from core (registry + lock file at `init`), which the provider ecosystem's size depends on.
4. **Language freedom *without* shipping a runtime** — gRPC made the protocol language-neutral, so the host bundles **no interpreter** and imposes **no toolchain on the host machine's PATH**; a plugin author brings whatever runtime they want. This is the R-3-shaped move: the host stays a single static binary across platforms *because* the guest runtime is externalized, not embedded.
5. **Why gRPC specifically over net/rpc:** wire-standard, multi-language, streaming, deadlines, HTTP/2 multiplexing — the exact features gob/netrpc lacked. The migration (protocol 4→5) shows the cost of choosing a non-portable wire format first: the whole provider ecosystem recompiled.

The honest counter-reading for SpecForge: go-plugin *externalizes* the interpreter instead of embedding one, and pays in process lifecycle, IPC copies, no fuel/timeouts by construction, and — critically — **zero guest containment**. It buys ergonomics and safety-from-crashes by splitting address spaces, and buys security only as distribution trust.

## 5. What SpecForge should learn

1. **go-plugin validates R-4 (trust machinery) and ignores R-2 (containment).** HashiCorp's 13-year conclusion is that *distribution trust and runtime containment are separable*: checksums, signing, registry review, and lock files matured; guest capability-scoping was never even attempted (their hostile-tenant answer is "containerize it"). SpecForge already built the trust half (signed registry, sha256 pinning); wasm is the containment half. The case study therefore supports KEEP_WASM with the registry as-is — and warns that no runtime choice substitutes for the missing capability enforcement (C7-04's fs allow-by-default would be *worse* than go-plugin's honesty: HashiCorp never pretends its guests are confined).
2. **The contract must precede the ecosystem — with an IDL, or it gets retrofitted painfully.** Terraform's stringly netrpc era is SpecForge's C7-03 (`call_export` + ad-hoc JSON). Their fix — immutable `.proto` per version, major versions as coexisting services negotiated at handshake, additive minors via feature detection — is exactly the WIT prescription in D08, including "serve two worlds side by side" (tfplugin5+tfplugin6 in one server ≈ WIT worlds `@1.0.0`/`@2.0.0`). Adopt the *pattern*: published immutable interface artifacts, negotiation, additive evolution; the technology (WIT vs proto) matters less than immutability-plus-negotiation.
3. **Deadlines that are declared must be enforced by the transport.** gRPC puts deadlines on the wire; go-plugin's hosts get watchdogs and health checks by construction. SpecForge declares `max_execution_ms = 30_000` and never reads it (C7-10). Wasmtime fuel/epoch is the in-process equivalent — the case study says: fix C7-10 at the runtime layer, not by convention.
4. **Stdio is a protocol channel — design the diagnostics path deliberately.** go-plugin's three-channel discipline (stdout = handshake only, logs = structured hclog over RPC, stderr = mirrored raw) exists because they learned the failure mode the hard way. SpecForge's plugin diagnostics today are `eprintln!` warnings that silently drop malformed pass output (D08 §1) — the same lesson is pending. A structured plugin-log channel in the host API is cheap and removes an entire class of "silent" failures.
5. **Workload shape decides in-process vs out-of-process.** Terraform plugins are I/O-bound adapters making small calls to slow APIs — process boundaries and RPC overhead vanish against network latency. SpecForge passes are CPU-bound over a 1.7k-entity snapshot with the whole graph pushed per call; an RPC boundary multiplies exactly SpecForge's worst cost (the per-pass memcpy), while wasm linear memory makes it one copy. HashiCorp never ran this workload, and their "we never needed more performance" caveat is workload-specific, not a law.
6. **Dogfooding is achievable without a trusted tier — see Vagrant/Waypoint, not Vault.** Vault's built-in/external split is the R-1 violation to avoid; Vagrant's "core implemented on the plugin API" and Waypoint's "built-ins built directly on the same plugin system as external plugins" are the R-1-honoring precedents. The enforcement mechanism that keeps builtins honest in SpecForge today (sync tests byte-comparing mirrors) is the sign the *runtime* isn't doing the enforcing — one runtime path with R-1 honored structurally deletes the mirrors (C7-11) the way Waypoint deleted its "special" built-ins.
7. **Debug ergonomics are a first-class feature, not an afterthought.** `TF_REATTACH_PROVIDERS` + test-mode in-process serving is why provider development is tolerable despite process isolation. SpecForge's R-5 hot reload is the same instinct; the borrowable idea is *reattach-style dev loop*: `specforge watch` should re-instantiate only the edited plugin's engine and diff diagnostics, and the SDK's test harness should be able to run a guest in-process and emit the equivalent of a reattach config.

## Verdict

**Verdict:** KEEP_WASM
**Confidence:** 4
**One-line rationale:** HashiCorp's 13-year record validates SpecForge's trust machinery (registry/signing/pinning) but never attempted guest containment — go-plugin processes hold the user's full privileges — while its hardest-won lessons (immutable IDL with negotiation, transport-enforced deadlines, structured log channels, one runtime for builtins and third parties alike) are all achievable inside the wasm model SpecForge already has, and the workload shape (CPU-bound passes over large snapshots) is the one out-of-process RPC handles worst.

## Bottom line

go-plugin = "externalize the runtime, trust the guest, enforce the channel." SpecForge has the opposite problem — it must contain the guest and keep a single static host binary, which wasm provides and go-plugin explicitly does not. Take the contract discipline (immutable, versioned, negotiated IDL → WIT), the enforced deadlines (fuel/epoch), the structured diagnostics channel, and the R-1 precedent from Vagrant/Waypoint; leave the process-per-plugin model, which HashiCorp's own README prices honestly ("shared libraries have much higher performance") and which fits Terraform's slow-I/O plugins, not SpecForge's batch analysis passes. Verdict unchanged: **KEEP_WASM**, confidence 4/5.
