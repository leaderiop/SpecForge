# Case Study — Figma's Plugin Architecture

**Fleet question:** what does the largest successful web-editor plugin ecosystem imply for SpecForge's KEEP_WASM vs LUA/PYTHON/TYPESCRIPT/MULTI decision?
**Method:** primary sources only — Figma's official developer docs, both canonical Figma engineering posts (2019), Figma's S-1/A SEC filing (July 2025), the `@figma/plugin-typings` repo (counted directly), and one long-horizon practitioner account. All facts below were fetched 2026-09-27; web_search was down, so every claim traces to a URL read directly.

## How Figma sandboxes plugins (and how it got there)

The commonly repeated summary — "iframe + postMessage" — is half right, and the half that is wrong is the interesting part. Figma's current model ([How Plugins Run](https://developers.figma.com/docs/plugins/how-plugins-run/)) is a **two-compartment split**:

1. **Plugin code runs on the editor's main thread inside a custom sandbox**: a minimal JS environment with modern language features (ES2020+: `async/await`, `BigInt`, `WeakRef`, `structuredClone`, typed arrays) but **no browser APIs** — no DOM, no `XMLHttpRequest`, no `setTimeout`. It talks to the document through the `figma` global with a **synchronous** API.
2. **The UI runs in a null-origin `<iframe>`** created by `figma.showUI(__html__)` ([Creating UI](https://developers.figma.com/docs/plugins/creating-ui/)). That iframe gets full browser APIs but **no access to the Figma scene**. The two halves communicate via `postMessage` (`pluginMessage` envelope; structured-clone-like semantics — no prototype chains, no `Blob`/`ArrayBuffer`, only `Uint8Array` carries binary).

The sandbox VM is **QuickJS, Fabrice Bellard's JS engine in C, cross-compiled to WebAssembly** — still true per Figma's docs and confirmed by practitioner [Tom MacWright (2024)](https://macwright.com/2024/03/29/figma-plugins): "part of your plugin in an iframe, where you display a UI, and part of it within QuickJS, where that code is able to actually read and write from your Figma document."

The journey to that design is the most transferable evidence Figma offers ([How we built the Figma plugin system](https://www.figma.com/blog/how-we-built-the-figma-plugin-system/), Rudi Chen, Aug 2019):

- **Attempt 1 — iframe sandbox with a copy-the-document API.** Plugins would `await figma.loadScene()`, mutate a copy, `await figma.updateScene()`. It failed on two measured grounds: (a) message-passing costs "~0.1ms per round-trip, which would only allow ~1000 messages per second," making a synchronous-feeling API impossible — async/await "is not user friendly" for their designer audience; (b) **serializing Microsoft's design-systems file took 14 seconds before the plugin could even run**. Lazy loading was rejected because it would force every API call to become asynchronous.
- **The main-thread decision:** to get a synchronous, intuitive API, plugins must run where the document lives. Accepted trade-off, stated verbatim: "Plugins can hang, and there is no way to interrupt a plugin" — mitigated socially (runs only on explicit user action; freeze is attributed to the plugin UI), not technically.
- **Attempt 2 — a JS interpreter compiled to WASM** (validated with Duktape, passing test262 ES5). Secure "in a way that's easy to reason about": the WASM engine has no browser APIs at all, so plugin code reaches the world **only through explicitly whitelisted host functions**. Kept as the backup plan.
- **Attempt 3 — the Agoric Realms shim** shipped at launch: fast (browser JIT) and debuggable with normal devtools, but every API endpoint had to be audited for inside/outside-object confusion — "the surface area created is too large." Figma's fix became their permanent pattern: implement the whole API over a **~500-LOC audited membrane** (`LowLevelJavascriptVm`: handles, `getProp`/`setProp`/`callFunction`), the membrane pattern, swappable over Realms *or* a WASM interpreter.
- **The 2019 incident** ([An update on plugin security](https://www.figma.com/blog/an-update-on-plugin-security/), Evan Wallace): multiple independent Realms-shim sandbox escapes (same-VM object confusion). Figma halted all plugin publishing, patched, audited published plugins, and in one week switched permanently to the backup: **QuickJS-in-WASM**, because "it's not possible to confuse objects from outside with objects from inside because the object representations are too different." Their explicit conclusion: human review "is about plugin user experience. We do not rely on human reviews to audit newly-published plugins for security… We instead use a sandbox to enforce a security boundary."

**Capability policy** (same post): plugins *can* run only on explicit user action, read/modify any data in the current file, talk to any server. They *can't* run by themselves, access anything when not running, read other files, learn project/team info, or alter Figma's UI outside their dialog. Network is capability-scoped by manifest: `networkAccess.allowedDomains` (down to individual URL paths) enforced as CSP violations, with the grant list **displayed publicly on the plugin's Community page** ([Manifest](https://developers.figma.com/docs/plugins/manifest/), [Network requests](https://developers.figma.com/docs/plugins/making-network-requests/)). Enterprise gets admin plugin whitelists. Plugin code is "live": updates propagate instantly to all open clients.

## Language and toolchain

Plugins are authored in **JavaScript/TypeScript**, bundled to one JS file (`main: "code.js"` in `manifest.json`). The launch motto: "If you can code a webpage with basic HTML and JavaScript, you can build a Figma plugin" ([launch post](https://www.figma.com/blog/introducing-figma-plugins/)). Figma publishes official TypeScript definitions ([figma/plugin-typings](https://github.com/figma/plugin-typings), MIT, active — last push 2026-09-23). I counted the current `plugin-api.d.ts`: **12,712 lines, 252 interfaces, 124 type aliases, ~1,814 members (~418 method signatures, ~1,223 properties)**. That `.d.ts` file is de facto the platform's IDL *and* its authoring ergonomics layer.

## API surface

One `figma` global, organized roughly as: the scene graph (`figma.root`, `currentPage`, `create*` factories, node properties like `opacity` as plain JS accessors), `figma.ui` (showUI/postMessage/resize), `figma.clientStorage` (async per-plugin KV), `figma.on(...)` events, `figma.notify`, plus a curated global `fetch` ("Figma Fetch API", CSP-enforced; historically network required the iframe). Storage quota: **5 MB per plugin**, scoped by plugin ID, explicitly "stored privately for **stability**, not **security**" ([clientStorage docs](https://developers.figma.com/docs/plugins/api/figma-clientStorage/)). The manifest carries `editorType` across five editors (figma, figjam, dev, slides, buzz) and `documentAccess: "dynamic-page"` — now required, because legacy plugins forced whole-file page loads ("Loading n pages for plugin…") ([Manifest](https://developers.figma.com/docs/plugins/manifest/)).

## Ecosystem size

- Aug 1, 2019 GA: **"over 40 public plugins" after 6 weeks of beta** ([launch post](https://www.figma.com/blog/introducing-figma-plugins/)).
- Figma's own S-1/A (SEC, filed 2025-07-28): users "have created **over 250,000 Community resources, including more than 10,000 plugins and widgets**"; timeline 2019 Figma Design plugins → 2021 FigJam plugins + widgets → 2025 Slides plugins; monetization enabled 2022 ([S-1/A](https://www.sec.gov/Archives/edgar/data/1579878/000162828025036090/figmas-1a2.htm)). Same filing: **13+ million monthly active users** (Q1 2025), $749.0M FY2024 revenue.
- Growth curve: 40 → 10,000+ in six years **on a platform of 13M MAU** — roughly 0.08% of MAU became published plugins+widgets.
- The ecosystem is real research infrastructure: arXiv indexes 4 recent papers built as Figma plugins (ICSME 2026 tool, CHI 2024, DIS 2026) ([arXiv query](https://arxiv.org/abs/2607.14830v2)).
- Mid-tail reality check: a successful indie plugin has ~11.3k "users"; Figma exposes no churn/active-user stats, so "users" is installation-flavored and up-only ([MacWright 2024](https://macwright.com/2024/03/29/figma-plugins)).

## Known limitations of the sandbox model

1. **Uninterruptible synchronous execution on the main thread.** A heavy plugin freezes the editor; there is no preemption. This was a *deliberate* 2019 trade-off, never revisited.
2. **Interpreter performance.** No JIT inside the QuickJS-WASM VM ("somewhat slower for certain plugins" — Figma's own words; MacWright: "the performance of Figma plugins is also not great").
3. **Debuggability.** MacWright: "When QuickJS encounters an issue in Figma, you get truly impenetrable errors. I've spent a lot of time just guessing what's going wrong." The debugging tax is the price of the VM boundary.
4. **Split-brain authoring.** Every UI-bearing plugin is two programs in two runtimes, stitched by `postMessage` with lossy serialization (no prototypes/methods, restricted binary types) and documented interception footguns (a neighboring plugin can navigate an iframe to the same URL and catch your messages unless you pass a `pluginId` and target origin) ([Creating UI](https://developers.figma.com/docs/plugins/creating-ui/)).
5. **Network is constrained twice** — null-origin CORS (only `Access-Control-Allow-Origin: *` servers callable from iframes) plus manifest CSP domains; and grant lists are public.
6. **Weak persistence.** 5 MB local KV; data vanishes if the plugin ID changes or the user clears cache.
7. **No background life.** Nothing runs headless, scheduled, or on-open; a plugin forgotten open shows a "Running…" toast until `closePlugin()` ([How Plugins Run](https://developers.figma.com/docs/plugins/how-plugins-run/)).
8. **Live-update risk.** Instant propagation to all open clients is great DX and a deployment weapon; Figma itself had to disable *all* publishing during the 2019 incident to close the exploit window.
9. **Security history.** The one same-process, same-VM sandbox they tried (Realms) was escaped within weeks; the VM/WASM boundary is what survived.

## What SpecForge should learn

SpecForge context: R-1 (no first-party tier), R-2 (untrusted plugins sandboxable), R-3 (single binary), R-4 (signed registry), R-5 (hot reload), R-6 (deterministic snapshots); current stack Extism/Wasmtime with `sandbox.rs`/`host_functions.rs`/JSON-over-`call_export`, audit findings C7-03 (no IDL), C7-10 (`max_execution_ms` unused) (`.plugin/evidence.md`, `.plugin/decision-brief.md`).

1. **"TYPESCRIPT vs KEEP_WASM" is a false dichotomy — Figma is the existence proof.** Figma's production sandbox *is* a scripting language hosted *inside* a WASM-compiled engine. The SpecForge equivalent is not `deno_core` (a second, native TCB): it is a QuickJS/quickjs-ng build to `wasm32-unknown-unknown` loaded as a guest through the *existing* Extism runtime. One sandbox, one capability boundary (R-1/R-2 preserved), TS/JS authoring for AI agents (criterion 2). Figma validated Duktape first with test262, then standardize on QuickJS — a 2019-era blueprint for exactly this composition, and Figma's "medium-size WASM binary" phrasing suggests a blob of the same order as SpecForge's 324–415 KB vendored guests, not a V8.
2. **The 14-second-serialization failure does not transfer — and that matters.** Figma went to extraordinary lengths (main thread, sync API, custom VM) because their documents are enormous and their API must feel synchronous to designers. SpecForge's host→guest handoff is a ~1.7k-entity graph snapshot — copy semantics over linear memory (`plugin.memory_new`, `crates/specforge-extism/src/host_context.rs`) are cheap at this scale. The pressure that forced Figma off message-passing is absent here, so SpecForge should not envy "native-feeling" embedding; it should fix the *protocol*, not the process model.
3. **The ~500-LOC membrane is the answer to C7-03.** Figma confine security-critical surface to one audited membrane, then layer hundreds of API members on top, and ship a 12.7k-line `.d.ts` as the public contract. SpecForge's stringly-typed `call_export` should get the same treatment: one tiny audited boundary (already exists as `host_functions.rs`) plus a *published* IDL — WIT or JSON Schema, with a generated `.d.ts`/bindings so the typing layer doubles as authoring DX. plugin-typings shows a hand-maintained `.d.ts` is a viable IDL at 1,800-member scale.
4. **Capability policy convergence validates R-2's shape.** Figma's can/can't list ≈ SpecForge's deny-by-default `SandboxPolicy`: no ambient fs, network only via declared grants, no cross-file/project access, no background execution, review-is-not-security. Their `networkAccess` manifest ↔ SpecForge's per-extension policy fields; their admin whitelist ↔ registry key pinning. Also adopt their incident posture: the ability to halt publishing instantly (they did) is part of the security design, and pairs with R-4's signed, integrity-checked installs.
5. **Import the costs as requirements, not surprises.** Interpreter-slowdown → keep wasmtime fuel/epoch interruption (fixes C7-10) rather than trusting guest cooperation. Debugging mush → invest in structured trap/diagnostic reporting over the boundary (criterion 8); WASM traps plus SpecForge's `emit_diagnostic` can beat Figma's stack-trace soup. Live-update risk → SpecForge's lockfile + hash verification should never be bypassable for speed.
6. **Discount the ecosystem argument.** 10k plugins took a 13M-MAU platform six years and yields ~0.08% penetration; SpecForge's authors are AI agents and a niche compiler audience. The case for TS authoring rests on authoring ergonomics for agents and the `.d.ts`-as-IDL effect — not on a Figma-scale network effect — and a quickjs-wasm guest can deliver it without betting the sandbox.

## Verdict

**Verdict:** TYPESCRIPT
**Confidence:** 3
**One-line rationale:** Figma's ten-thousand-plugin ecosystem runs on TypeScript/JS authored against a 12.7k-line `.d.ts`, but executes inside a QuickJS-compiled-to-WASM sandbox behind a ~500-LOC capability membrane — so SpecForge should add TS authoring *as a quickjs-wasm guest inside the existing Extism/Wasmtime sandbox*, not as a native embed or a runtime replacement.

## Bottom line

**TYPESCRIPT** — confidence **3/5**. Figma proves the winning combination is a scripting authoring surface (TS/JS, typed via `.d.ts`-as-IDL) hosted *inside* a WASM sandbox with an explicitly capability-scoped host API; SpecForge can replicate that exactly by loading a QuickJS-WASM engine as a plugin guest under its existing R-1..R-6 model, taking Figma's membrane/IDL discipline and its unbounded-sync-execution anti-lesson while ignoring its ecosystem-scale envy.
