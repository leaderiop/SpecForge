# Installing into a host

What you get: the agents, skills, slash commands and hooks your project's extensions contribute, written into the
project-local files of the agent host you use (Claude Code, Codex, Cursor), together with SpecForge's own MCP server
entry and its spec guard. The files are generated: install owns exactly what it marked, and nothing else.

```bash
specforge install claude-code            # one or more hosts: claude-code, codex, cursor
specforge install claude-code --dry-run  # the plan, nothing written
specforge install claude-code --check    # the plan; exit 1 when anything would change (CI)
specforge install claude-code --force    # also rewrite a file install wrote that was edited since
specforge uninstall claude-code          # remove exactly what install wrote
```

A project whose extensions contribute nothing to a host gets the MCP entry and the spec guard only.

## What is written

| | Claude Code | Codex | Cursor |
|---|---|---|---|
| MCP server `specforge` | `.mcp.json` | `.codex/config.toml` | `.cursor/mcp.json` |
| agents | `.claude/agents/<id>.md` | `.codex/agents/<id>.toml` | `.cursor/agents/<id>.md` |
| skills and slash commands | `.claude/skills/<id>/SKILL.md` | `.codex/skills/<id>/SKILL.md` | `.cursor/skills/<id>/SKILL.md` |
| hooks | `.claude/settings.json` | `.codex/hooks.json`, `.codex/config.toml` | `.cursor/hooks.json` |
| statusline | `.claude/settings.json` | not rendered | not rendered |

A slash command is a skill named `<short>-<route>` holding a trampoline: it calls the extension's prompt or command
through its own surface (the MCP tool, or the CLI without the MCP server), so the workflow, its gates and its writes
are the same as from any other surface.

**Codex and Cursor are unverified.** The Claude Code layout and hook protocol follow its documentation. The Codex and
Cursor file layouts and hook protocols were written from the plan and could not be checked against those hosts here:
their golden files and recorded hook inputs are the plan's, not the hosts'. Whatever a host cannot take (Cursor's
statusline and `pre_compact`, Codex's statusline) is reported in the install outcome as `not_rendered`, never
written. Treat Codex and Cursor output as a draft until you have run it in the host.

## Ownership

Install writes a file, or an entry in a shared config file, only when it can recognise it as its own.

- An owned Markdown or TOML file starts with `# generated by specforge install (<host>) from <extension>@<version>
  <kind> <id>; edits are overwritten; sha256:<digest>`; the digest covers the file without that line.
- An owned hook entry in `settings.json` or `hooks.json` is one whose command ends with the comment
  `# specforge-install`, and the MCP server is the entry named `specforge` of `mcpServers` (or `[mcp_servers.specforge]`
  in `config.toml`). A hook of yours that only mentions `specforge hook` is yours, and stays.
- Everything else is never written, moved or removed: your own hooks, other MCP servers, settings, hand-written agents.
  Uninstall strips only what install marked, and deletes a config file only if install created it and nothing else is
  left in it.
- Install never follows a link. A symbolic link where it would write or remove a file, or in the path to it (a linked
  `.claude/`, a dangling `agents/x.md`), is refused and nothing is written.

| Disk | Install does |
|---|---|
| nothing there | creates it |
| the same bytes | `unchanged`: a second install writes nothing |
| marked, not edited, different | updates it |
| marked, edited by hand | refuses `edited_file`; `--force` rewrites it |
| there, no marker | refuses `foreign_file`, always |
| marked, no longer contributed | removes it (an edited one is refused without `--force`) |

Refusals are reported together and nothing is written. Otherwise the plan is one change under the project's write
lock, journaled like any other write: a kill in the middle is put back by the next writer. Uninstall plans the removal
of every marked file and owned entry, and an emptied `skills/<id>/` directory goes with them.

## Drift

`specforge doctor` reports, as warnings and only for a host directory that holds a marker:

- `host_file_edited <path>`: a file install wrote was edited since;
- `host_install_stale`: install would write something other than what is on disk now (an extension was upgraded, a
  setting a render reads changed, a contribution was added or removed).

Run `specforge install <host>` again to bring the files up to date. `install --check` is the same comparison for CI.

## The spec guard

Every install wires the host's own hook `core.spec_guard` on a Write or Edit of a `.spec` file (on Codex and Cursor
also on a patch-text tool, read from its `*** Update File:` sections; those two hosts are drafts, tested against
goldens, not a run of the host). It judges the file as
the write would leave it, like a hand edit, and denies a write that sets a computed value, a harness value with no
ledger line, or a kind or field only a person writes, naming the entity, the field and the tool. Any other error the
write would add is returned to the agent as context. It is a boundary of the host's tools, not of the file system: a
person or a shell command can still write the file.

The guard fails closed where it can: an event over 4 MiB, or one that is not the host's JSON, is denied. It cannot fail
closed where the host never starts it. A host started from a desktop launcher may not have `specforge` on its PATH, and
then no hook runs; install writes the bare command name, and `doctor` cannot see the host's PATH. A hook that the
project no longer declares (an extension was removed and install not run again) is a no-op with a line on stderr, and
`doctor` reports the stale install. On a very large project the compile the guard runs may outlast the host's own hook
timeout, and the host then lets the write through: it has no deadline of its own.
