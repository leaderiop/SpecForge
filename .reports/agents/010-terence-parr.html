## Naming Conventions

Any valid identifier is accepted for all entity kinds. There is no enforced case convention.

```ebnf
identifier = ( letter | "_" ) , { letter | digit | "_" } ;   (* 1-60 chars, E014 *)
```

Identifiers must be 1-60 characters. The graph-build pass enforces the range
and emits `E014` with the offending span:

```rust
// crates/specforge-graph/src/build.rs
const MAX_IDENT: usize = 60;
if raw.is_empty() || raw.len() > MAX_IDENT {
    diags.push(Diagnostic::error("E014", format!(
        "identifier '{raw}' must be 1-{MAX_IDENT} characters (got {})" , raw.len()
    )).with_span(span));
}
```

Proposed solution. Pick one: add a length check in graph build (E-code with span) and keep the EBNF, or amend the doc to match the regex. Prefer enforcing with a clear suggestion.

The formatter's recovery is textbook ANTLR-style: when the parse fails, format_with_parse_errors (crates/specforge-formatter/src/engine.rs:1143-1292) identifies each error region and copies it verbatim into the output — whitespace preserved byte-for-byte — while reflowing surrounding well-formed code, and the idempotency invariant is explicitly tested. It emits F011 warnings naming the preserved line ranges so users can find their mistakes. Additionally, parse_incremental exists alongside parse, and triple-quoted strings preserve newlines and indentation (parse_test.rs:1050-1245). Users can trust specforge format on broken files, which few formatters can honestly claim; the only gap is that this behavior is undocumented.
