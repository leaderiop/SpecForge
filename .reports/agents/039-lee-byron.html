Auditor review

Lee Byron (GraphQL): One envelope, format_version 2.0, three incompatible node shapes across json/context/brief — this is the kind of implicit variant that breaks clients six months out, and the single published schema already rejects valid context exports. Pick one: a variant discriminator field with per-variant $defs, or three published schemas with distinct $ids. I'd also reconsider cloning the full schema into every brief export; a $ref with the content hash you already compute would do.

emit_json_with_schema, emit_context_with_schema and emit_brief_with_schema (schema.rs:369, 417, 474) all stamp format_version 2.0 and schema_version, but their node objects differ radically: JsonNodeV2 carries {id,kind,title,file,line,fields}, ContextNodeV2 carries {id,kind,title,contract,status,verify} with no file/line/fields, and BriefNodeV2 carries only {id,kind,title}. A consumer cannot tell from the envelope which node shape to expect, and the single published graph-protocol schema (which requires file/line/fields) rejects valid context and brief exports. This is the same 'one version, three contracts' trap that breaks agent tooling silently.

#[derive(Serialize)]
struct ContextGraphV2 {
    format_version: &'static str,      // "2.0-context"
    variant: &'static str,             // "context" | "brief" | "full"
    schema_version: String,
    schema: GraphProtocolSchema,
    nodes: Vec<ContextNodeV2>,
    edges: Vec<JsonEdge>,
}

impl ContextGraphV2 {
    fn envelope(format: &'static str, variant: &'static str,
                schema: &GraphProtocolSchema) -> Self {
        Self {
            format_version: format,
            variant,
            schema_version: schema.schema_version.to_string(),
            schema: schema.clone(),
            nodes: Vec::new(),
            edges: Vec::new(),
        }
    }
}
