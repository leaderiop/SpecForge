Solution prose leaks machine counts into the problem domain — numbers that will rot silently

103 Michael A. Jacksoneffort Smoves: root_extension_declaration_coverage
Evidencespec/product/features.spec:14-83 — solutions cite '9 entity kinds, 16 edge types', '26 query methods', '16 CLI commands', '47 declarative validation rules', '55 diagnostic codes' — counters duplicated from manifests with no linkagespec/governance/decisions.spec:252-289 — config_driven_kind_registry ADR explicitly warns kind sets change; the counters contradict that fluidity

The problem/solution prose in spec/product/features.spec hard-codes inventory numbers — '9 entity kinds, 16 edge types', '26 query methods', '16 CLI commands', '47 declarative validation rules', '55 diagnostic codes' — duplicated from manifests with zero linkage. ADR config_driven_kind_registry explicitly establishes that kind sets change as extensions load, so every one of these digits is a promise the architecture says will be broken; when the 17th CLI command ships, the prose lies silently and no diagnostic fires. Solution prose should reference the entities ('the kinds registered by the manifest'), not quote counters that belong to the registry.

Explain like I'm 10

The 'why we built it' paragraphs quote exact inventory numbers, like explaining why you bought a shelf by saying it holds exactly 26 books. Buy one more book and the sentence is a lie — and nothing flags it. Say 'the whole collection', not '26 books'.

Proposed solution. Replace literal counts in problem/solution prose with references to the manifest entities (or drop them); a lint that warns on digits in solution prose would catch future rot.
