SpecForge fails its own written spec: export max_tokens contract unimplemented and undetected

highC9-02
067 Den Delimarskyeffort Mmoves: token_budget reachable from surfaces

PRD-007's token-budget contract says export must accept a size limit, but the specforge.export MCP descriptor exposes only format and scope - no max_tokens - and tools/export.rs builds EmitOptions via ..EmitOptions::default(), leaving token_budget None even though EmitOptions and budget.rs fully implement truncation. The CLI export.rs run() likewise hardcodes token_budget: None and takes no --max-tokens flag. So the project's own spec is violated by its own binary, and nothing detects it: there is no CI gate that walks behavior contracts naming tool params/CLI flags and asserts they exist. This is the SDD dogfooding failure an auditor of an SDD vendor should flag first.

McpToolDescriptor {
    name: "specforge.export".into(),
    description: "Export the graph in various formats".into(),
    input_schema: json!({
        "type": "object",
        "properties": {
            "format": { "type": "string", "enum": ["graph", "context", "brief"], "default": "graph" },
            "scope": { "type": "string", "description": "Scope to entity subgraph" },
            "max_tokens": { "type": "integer", "minimum": 1,
                "description": "Token budget; output is truncated by degree-centrality priority when exceeded" }
        }
    }),
    category: Some("core".into()),
}

// tools/export.rs - honor it:
let max_tokens = args.get("max_tokens").and_then(|v| v.as_u64()).map(|v| v as usize);
let options = EmitOptions { format: fmt, scope, token_budget: max_tokens, ..EmitOptions::default() };
// CLI mirrors it as specforge export --max-tokens N; a CI test walks behavior
// contracts naming flags/params and asserts each exists in registry + clap defs.

Explain like I'm 10

The company wrote its own rulebook saying 'our export button must have a size dial' — and the button has no dial. The whole pitch of spec-driven development is that the spec catches drift between what you wrote and what you built; here the project's own spec is being violated and no alarm rings. For an SDD competitor's auditor, that's the finding: the method wasn't applied to the product.

Proposed solution. Add max_tokens to the MCP export schema + args and a --max-tokens CLI flag, then run the PRD-007 loop on the project itself: specforge.trace/validate against spec/behaviors should be a CI gate (e.g., a test that walks behavior contracts naming CLI flags/tool params and asserts they exist).
