Domain failures masquerade as -32602, starving the re-ask loop

mediumC9-12
075 Shreya Rajpaleffort Smoves: MCP notifications conformance

error_codes.rs defines only the five JSON-RPC standard codes, so every domain failure - unknown export format in export.rs, unknown kind in prompts/infer.rs, unknown entity in query/find_definition - is stamped -32602 INVALID_PARAMS, the code reserved for structurally malformed requests. The same stamp is even reused for server-not-initialized (-32600) in registry.rs and tools/mod.rs. A guardrail/re-ask loop depends on distinguishing your-argument-value-was-wrong from your-frame-was-malformed, and without a dedicated app-error range plus machine-readable data the agent can only guess. registry.rs descriptors already carry enum lists for formats and kinds, so the valid-values payload costs nothing to produce.

// error_codes.rs
pub const SERVER_NOT_INITIALIZED: i64 = -32002;
pub const DOMAIN_ERROR: i64 = -32000; // app range: unknown_kind, unknown_format, ...

// shared helper, used by export/query/etc.
pub fn domain_error(id: Option<Value>, kind: &str, message: String, valid: &[&str]) -> JsonRpcResponse {
    JsonRpcResponse::error_with_data(id, DOMAIN_ERROR, message, serde_json::json!({
        "error_kind": kind,
        "valid_values": valid,
    }))
}

Explain like I'm 10

A guardrail loop works by the validator telling the model precisely which rule it broke so it can fix and retry. Here 'you passed an enum value we don't offer' and 'your request was malformed garbage' get the same error stamp, with no machine-readable hint of valid values. The agent must guess instead of re-asking smartly.

Proposed solution. Define an app error-code range (-32000s) for domain failures (unknown_kind, unknown_format, unknown_entity), always attach data with valid enum values (the descriptor enums are already in registry.rs), and route through error_with_data.
