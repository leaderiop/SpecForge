Auditor review

Max Brunsfeld here: the zero-domain grammar with `word: $.identifier` and empty conflicts is exactly how I'd build a spec DSL parser — it will never need touching when you add entity kinds. But shipping tree-sitter without a single corpus test is leaving its best feature on the table; error recovery especially is only trustworthy when pinned fixture-by-fixture. And your extractor trusts the tree blindly: check root.has_error() and walk is_missing nodes, or tree-sitter's silent repairs flow straight into your typed graph.

MISSING nodes/root.has_error() never inspected; some syntax errors emit no E001

highC3-00
012 Max Brunsfeldeffort Mmoves: Missing-node diagnostics
Evidencespecforge-parser/src/parse.rs:107-133,169-205 — only ERROR children handled; no has_error/is_missing checkspecforge-formatter/src/engine.rs:245-248 — correct is_error/is_missing pattern exists here

parse_incremental in specforge-parser/src/parse.rs only surfaces diagnostics when a top-level child has kind ERROR. Tree-sitter also reports failures via root.has_error(), is_missing() nodes, and ERROR nodes nested deeper than the first level (e.g. inside an entity_block); the match arm `_ => {}` silently swallows all of these. The observable consequence is a syntax error that produces SpecFile.errors == [] while the tree is corrupt, so downstream phases (graph build, validation, LSP publish) run on a partially-extracted AST with no E001 emitted. The formatter already models the correct pattern: specforge-formatter/src/engine.rs collect_errors_recursive checks node.is_error() || node.is_missing() on every node. For a typed-graph compiler consumed by AI agents, a silently-corrupt tree is the worst failure mode: the agent receives plausible but wrong diagnostics instead of a parse error.

Zero tree-sitter corpus tests

mediumC3-01
012 Max Brunsfeldeffort Smoves: Corpus coverage
Evidencetree-sitter-specforge/tests:dir — only queries.rs; no corpus dir

crates/tree-sitter-specforge/tests contains only queries.rs (highlight/fold query validation); there is no corpus/ directory, so tree-sitter test has zero fixtures to run. Every grammar change is validated only indirectly, through specforge-parser integration tests that assert on the extracted AST, which conflates grammar correctness with extractor correctness. Recovery behavior (the ERROR/MISSING cases from C3-00) is exactly where tree-sitter's corpus format shines: expected output trees pin down how partial input reparses. The grammar is 240 lines with dedicated use/spec/ref/define rules plus a generic entity_block — a handful of corpus files per rule would lock all of it in for an afternoon of effort.

Zero-domain grammar, word rule, empty conflicts — right shape

infoC3-02
012 Max Brunsfeldeffort Smoves: Corpus coverage
Evidencegrammar.js:header/conflicts/word — 4 dedicated constructs; zero-entity guard tests enforce no core keywords

grammar.js opens with an explicit design principle of zero domain knowledge: only use_import, pub_use_import, spec_block/ref_block/define_block plumbing, and the generic entity_block exist as constructs, conflicts is empty, and word is anchored on $.identifier so keyword recognition never tokenizes a closed keyword list. The parser accepts ANY keyword and defers validation to the semantic phase, which is why adding a new entity kind requires zero grammar changes.

exemplar — the good pattern
// Design principle: ZERO domain knowledge in core.

//   - spec (singleton project root)
//   - ref (scheme.kind:identifier compound ID)
//   - define (user-defined entity types)
//
// Everything else is parsed by the generic entity_block rule.
// The parser accepts ANY keyword — validation happens in the semantic phase.
