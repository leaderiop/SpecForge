The .spec contracts declare tool parameters and CLI flags as intended behavior, but nothing checks that registry.rs descriptors or the clap command definitions actually honor them - the declarations are compiled for consumers yet never compiled against the implementation, which is the exact gap DSPy's declarative model exists to close. The dispatch arms in tools/mod.rs are hand-bound strings; nothing asserts each arm has a registry entry with matching required params. The C9-02 max_tokens drift is one concrete instance; a conformance pass walking behavior contracts into fixtures and asserting against registry + clap turns the whole class into a CI failure under nextest.

// generated fixture from behavior contracts (build step or test helper):
// { tool: specforge.export, params: [format, scope, max_tokens], flags: [--max-tokens] }

#[test]
fn tool_contracts_match_registry_and_cli() {
    for contract in load_contract_fixtures("spec/") {
        let descriptor = find_tool(&registry(), &contract.tool)
            .unwrap_or_else(|| panic!("{} missing from MCP registry", contract.tool));
        for param in &contract.params {
            assert!(descriptor_schema_has_param(descriptor, param),
                "{} schema missing param {}", contract.tool, param);
        }
        for flag in &contract.cli_flags {
            assert!(clap_command_accepts(flag), "CLI missing flag {}", flag);
        }
    }
}

Explain like I'm 10

DSPy's lesson is that you declare the program and a compiler keeps the pieces honest against metrics. Here the declarations exist (contracts naming flags and parameters) but there is no compiler pass checking that the program — the CLI and MCP code — satisfies them. The spec is a beautiful, unenforced wishlist.

Proposed solution. Add a conformance test generator: parse behavior contracts for tool/flag names into a fixture, and assert registry.rs descriptors + clap command definitions satisfy them; wire into CI nextest run.
