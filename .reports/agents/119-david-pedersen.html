publish_package, yank_package and verify_auth in handlers.rs each repeat the identical sequence: extract the authorization HeaderMap entry, call auth::validate_bearer, then auth::token_has_scope, each branch hand-building (StatusCode, Json(serde_json::to_value(ErrorResponse{..}).unwrap())) tuples. Beyond the copy-paste drift risk (a future handler may forget the scope check), every response construction calls serde_json::to_value(...).unwrap() - a panic path if any field ever becomes non-serializable. A FromRequestParts extractor (AuthToken with required scopes) plus a small ApiError IntoResponse type centralizes the policy and removes the unwraps.

use axum::{
    extract::FromRequestParts,
    http::request::Parts,
};

impl FromRequestParts<Arc<AppState>> for AuthToken {
    type Rejection = ApiError;

    async fn from_request_parts(
        parts: &mut Parts,
        state: &Arc<AppState>,
    ) -> Result<Self, Self::Rejection> {
        let header = parts
            .headers
            .get("authorization")
            .and_then(|v| v.to_str().ok())
            .ok_or(ApiError::unauthorized("missing Authorization header"))?;
        let record = validate_bearer(&state.database, header)
            .ok_or(ApiError::unauthorized("invalid or revoked token"))?;
        Ok(AuthToken(record))
    }
}

token_has_scope uses bare starts_with - scope prefix matches unrelated package names

mediumC14-06
119 David Pederseneffort Smoves: Server hygiene
Evidencecrates/specforge-registry-server/src/auth.rs:32-40 — token_has_scope returns package_name.starts_with(scope); a token scoped to web authorizes webui and web-framework etc. No delimiter or boundary check.

token_has_scope in crates/specforge-registry-server/src/auth.rs (lines 32-40) authorizes with package_name.starts_with(scope), so a token scoped to web is accepted for webui, web-framework and even website-admin. For a registry that AI agents hit with publish credentials, a leaked narrowly-scoped token grants a far larger blast radius than the user granted. npm-style semantics - exact match, or package starts with scope followed by a / boundary - closes it, and the near-miss case deserves a unit test.

pub fn token_has_scope(record: &TokenRecord, package_name: &str) -> bool {
    match &record.scope {
        None => true,
        Some(scope) => scope_matches(scope, package_name),
    }
}

/// npm-style boundary match: the scope is the whole name, or a
/// namespace prefix followed by a path separator.
fn scope_matches(scope: &str, package_name: &str) -> bool {
    package_name == scope
        || package_name
            .strip_prefix(scope)
            .is_some_and(|rest| rest.starts_with('/'))
}

#[test]
fn scope_respects_name_boundary() {
    assert!(scope_matches("web", "web"));
    assert!(scope_matches("web", "web/dep"));
    assert!(!scope_matches("web", "webui"));
    assert!(!scope_matches("web", "web-framework"));
}
