Auditor review

Hejlsberg's praise goes to FieldRegistry: the typed vocabulary of 8 field types with edge and target_kind metadata is the right data, in the right place, ignored by every surface that should consume it. His first fix would be making the type system visible — specforge model tables and LSP hover fed straight from the registry, no re-derivation. He would note that IntelliSense-quality tooling is what turns a DSL from a file format into a language. Document the 8 types once and never let a second source of truth appear.

FieldRegistry already carries a complete typed vocabulary — ManifestFieldType with String, Integer, Bool, Enum(Vec), StringList, Reference, ReferenceList, Block — plus edge/target_kind/inverse_of/required metadata in FieldRegistryEntry (crates/specforge-registry/src/registries/field.rs:3-18), exactly the data needed for editor completions, signature help, and honest docs. But quick-reference.md field tables show only Required/Optional name lists with no types or enum values, and the LSP would have to re-derive types instead of serving them from the registry. The compiler knows each field is a number or a pick-one-from-list and never tells the author. Expose it once: per-kind field-type tables in specforge model output, LSP hover/completion fed from FieldRegistry directly, and the 8 types documented once in entity-model.md.

## Field Types

Every registered field has one of eight types (source of truth: `FieldRegistry`,
mirrored into `specforge model` output and LSP hover):

| Type | Meaning | Example |
|------|---------|---------|
| string | free text | title |
| integer | whole number | coverage.percent |
| bool | true/false | file_reference |
| enum | one of fixed options | status: draft, active, done |
| string_list | list of strings | tags |
| reference | edge to one entity of target_kind | invariants (to invariant) |
| reference_list | edge to many entities | behaviors (to behavior) |
| block | nested structured block | contract |

`specforge model feature` prints this table per kind; the LSP serves the same
data for completion and signature help.

The compiler knows each field is a number, a yes/no, or a pick-one-from-list — but never tells the person typing. It is like a form where the boxes are secretly typed. Publishing the types turns guessing into autocomplete.

Proposed solution. Emit a per-kind field-type table (types, enum options, required) into `specforge model` output and feed LSP hover/completion from FieldRegistry directly; document the 8 field types once in entity-model.md.
