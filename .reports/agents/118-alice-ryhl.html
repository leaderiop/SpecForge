Backend::index_workspace in crates/specforge-lsp/src/backend.rs runs WalkDir traversal, std::fs::read_to_string and specforge_parser::parse synchronously inside an async fn, and takes self.state.write().await once per file inside the loop. initialize awaits it, so opening a project with a large (or accidentally huge, pre-SKIP_DIRS-hygiene) workspace blocks the tower-lsp runtime thread - no requests, no cancellation, editor hang. A grep confirms zero spawn_blocking in the crate. Moving the walk/parse loop into tokio::task::spawn_blocking and taking the write lock once afterwards fixes both the blocking and the per-file lock churn.

        // Walk, read and parse off the async runtime; take the write lock once.

A restaurant where the waiter personally cooks every dish: while one big order (indexing a large workspace) cooks, no other waiter can take orders - the editor freezes. Hand the cooking to the kitchen staff and only serve the result.

Proposed solution. Wrap the walkdir/parse loop in tokio task spawn_blocking collecting parsed files; take the write lock once after the blocking pass (also removes per-file lock churn).

No spawn_blocking in the crate.

In crates/specforge-registry-server/src/handlers.rs, search_packages calls state.database.search (a synchronous rusqlite query) directly inside an async fn; publish_package buffers field.bytes().await for the wasm upload with no size limit and then runs the full SHA-256 synchronously over the buffer; download_package calls the synchronous state.storage.read_wasm. None of these run on the blocking pool, so one slow sqlite query or large upload stalls every other request on that worker. A grep confirms no spawn_blocking in the crate and no DefaultBodyLimit on the router. Wrapping the sqlite/storage calls in spawn_blocking and adding axum DefaultBodyLimit (e.g. 64 MiB) closes both the latency and the memory-exhaustion holes.
