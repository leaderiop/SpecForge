The root manifest spec/specforge.spec declares only three extensions (@specforge/software, @specforge/product, @specforge/governance), yet the corpus ships and heavily uses a fourth: spec/extensions/formal/ contains 4 accepted ADRs (formal_extension_split etc.), feature/behavior/invariant/manifest specs for @specforge/formal, and the glossary defines its vocabulary (t_proof_obligation, t_sync_block, t_progressive_formality). Any agent compiling the graph trusts the extensions list as the authoritative module set, so @specforge/formal entities are invisible to dependency/coverage reasoning from the root alone. Nothing cross-checks the extensions/ directory against the declared list, so the discrepancy persists silently. For a project whose pitch is a machine-checkable context standard, the root config falsifying the corpus is exactly the class of drift the tool should catch.

Explain like I'm 10

The cover page of the manual lists three authors, but the book has four chapters and chapter four is signed. Anyone trusting the cover page gets the wrong idea about what the project actually is. The machine-checked config says one thing; the machine-checked content says another — and nothing catches it.

Proposed solution. Add @specforge/formal to specforge.spec extensions (or explicitly document why the self-host corpus excludes it, as a decision entity). Better: add a validator rule W-level 'extensions/ directory contains manifest specs for extensions not declared in the spec root'.

'Faked rational process' is real but one-sided: the corpus documents the design, not the deviations (wasi vs unknown-unknown build assumption undocumented in spec)

Explain like I'm 10

The manual says 'batteries included', but nobody wrote down what kind of batteries or that the battery compartment is empty until you assemble it yourself. A spec should record the assumptions someone must satisfy to build from a fresh clone, not just the happy design.

Proposed solution. Record the build assumption (wasm32 target, bootstrap requirement for embedded builtins) as either a constraint or a failure_mode in spec/governance/, so the compiled spec carries the operational truth docs/ and CI forget.
