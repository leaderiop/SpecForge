The vscode-published schema (schema/specforge.schema.json) declares additionalProperties:false with ~17 keys (strict, namespace, providers, personas, coverage, ...) while ProjectConfig (crates/specforge-common/src/project.rs:27-34) reads only name, version, spec_root, extensions and inference — and inference is not in the published schema at all, so an editor red-squiggles the exact key the compiler consumes, while compiler-ignored keys like strict validate fine and do nothing. The two hand-maintained artifacts drift in both directions; package.json:188-190 binds the editor to the stale copy with no CI check. Short term: add inference to the schema, mark aspirational keys reserved, and CI-compare the copy; long term derive the schema from serde-serialized ProjectConfig.

The CLI compile path routes CycleDetection patterns to detect_cycles (compile.rs:463-466) and reports cycle errors, but the LSP diagnostic pass explicitly `continue`s on the same pattern kind (backend.rs:409-413), so an editor shows a clean file while the CLI build fails — the classic 'clean in editor, red in CI' agent-hostile divergence. The cycle-walking code lives privately in specforge-emitter::compile, so the LSP cannot reuse it. Promoting detect_cycles into specforge-registry (which both sides already depend on for validation_engine) and calling it from the LSP debounced on change makes both surfaces enforce the identical rule.
