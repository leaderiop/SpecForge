One construct, two parses: bare `verify "..."` vs `verify <kind> "..."` coexist in the corpus

mediumC12-15
109 John MacFarlaneeffort Smoves: provider_syntax_drift
Evidencespec/events/compilation.spec:80-81 — event extension_manifests_loaded uses `verify "Extension manifests MUST be loaded..."` with no kindspec/events/compilation.spec:36-37,51-53 — sibling events use `verify integration "..."`spec/glossary.spec:701-712 — t_verify_statement defines the syntax as `verify <kind> "description"` — the bare form contradicts the project's own glossary

Two verify syntaxes coexist in the corpus: the dominant verify kind string form (e.g. verify integration in spec/events/compilation.spec:36-37,51-53) and a bare verify string at compilation.spec:80-81 (event extension_manifests_loaded). The project's own glossary entry t_verify_statement (spec/glossary.spec:701-712) defines the syntax as verify kind description, so the bare form contradicts the documented grammar and leaves readers and tools guessing what kind the declaration has. Either make the kind optional with defined default semantics in the glossary, or emit a diagnostic on the bare form and fix the occurrence — glossary and grammar must agree.

before — current code
event extension_manifests_loaded {
  channel internal

  payload {
    extensionCount  integer
    manifestPaths   string[]
    timestamp       timestamp
  }


  verify "Extension manifests MUST be loaded before populating the kind registry"
}

↓ fix ↓
after — proposed fix
event extension_manifests_loaded {
  channel internal

  payload {
    extensionCount  integer
    manifestPaths   string[]
    timestamp       timestamp
  }


  verify integration "Extension manifests MUST be loaded before populating the kind registry"
}

Explain like I'm 10

The form has a line for 'type of check', but some forms are filed with that line blank and still accepted. Now every reader (and program) has to guess what an unchecked box means. One syntax, one meaning — that is the whole game.

Proposed solution. Either make the kind optional with defined default semantics (and document it in t_verify_statement) or emit a diagnostic on the bare form and fix the occurrence; the glossary and grammar must agree.

Prose/DSL boundary mostly right, but acceptance criteria and flows are unchecked prose inside typed entities

Evidencespec/product/features.spec:18-23,52-56 — acceptance [ "..." ] is free strings (ADR pe_acceptance_free_form:148 accepted this deliberately)spec/product/journeys.spec:34-41 — flow prose likewise

The prose/DSL boundary is mostly right — typed fields for facts, free-text boxes for stories — but acceptance [ ... ] in spec/product/features.spec and the flow prose in journeys hold checkable promises ('All 9 entity kinds registered in KindRegistry after manifest load', 'All 16 CLI commands respond to --help') as pure strings. ADR pe_acceptance_free_form accepted this deliberately, but unchecked promises are wishes with formatting: nothing distinguishes a narrative criterion from one a verify block could prove. Tag a subset of acceptance strings with references to behavior verify blocks (e.g. acceptance_verify) so at least the checkable slice becomes compiled and covered, and document the deliberate boundary in docs/entities/spec.md.

The form has typed boxes for facts and free-text boxes for stories — a good split. But the free-text boxes quietly hold promises ('all 16 commands respond to --help') that someone will want to check later, and unchecked promises are just wishes with formatting.

Proposed solution. Keep prose where it belongs, but tag checkable acceptance strings (e.g. acceptance_verify referencing behavior verify blocks) so at least a subset is compiled; document the deliberate prose boundary in docs/entities/spec.md.
