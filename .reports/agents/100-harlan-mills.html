Contract verifies are template boilerplate: every behavior ends with 'requires/ensures consistency for X' — certification value near zero

mediumC12-02
100 Harlan Millseffort Lmoves: behavior_verify_coverage
Evidencespec/behaviors/formatting.spec:42,73,105,136 — verify contract strings are mechanically derived from the behavior titlespec/behaviors/parsing.spec:38,71,100,141 — same pattern; unit verifies are specific, contract verifies are not

Nearly every behavior in spec/behaviors/ ends with a contract verify of the form verify contract "requires/ensures consistency for X" where X is mechanically derived from the behavior title — e.g. 'requires/ensures consistency for spec file formatting' (formatting.spec:42) and 'requires/ensures consistency for in-memory graph construction' (graph.spec:38). Unlike the unit verifies, which name concrete observable outcomes, these strings assert nothing falsifiable and cannot map to any real test. Yet W017-style coverage counting treats them as contract-level coverage, inflating declared coverage with zero-information rows. The DSL already supports real Design-by-Contract requires/ensures blocks (used richly in behaviors/infer.spec), so the ceremonial line is noise wearing a verification badge.

Explain like I'm 10

Every recipe ends with the same sentence: 'tastes like it should.' It is true of every dish and therefore tells you nothing about any dish. The specific steps above it are good; the universal closing line is noise wearing a verification badge.

Proposed solution. Either give contract verifies real requires/ensures pairs (the DSL already supports Design-by-Contract blocks) or drop the ceremonial `verify contract` line; W017-style lint should not count it as coverage.

Implemented features still marked `status proposed` — spec status is a stale mirror of reality

mediumC12-03
100 Harlan Millseffort Smoves: behavior_verify_coverage
Evidencespec/features/infer.spec:24-26,45-47,67-69,88-90 — all 4 infer features carry status proposedspec/behaviors/infer.spec:18-418 — 18 implemented behaviors for those features, including shipped diagnostics I200/I202 and MCP tools

All four inference features in spec/features/infer.spec still carry status proposed, while spec/behaviors/infer.spec defines 18 fully specified behaviors — including shipped diagnostics I200/I202, MCP tools, and unit verifies for manifest load/save. The spec status field is therefore a stale mirror of reality: an agent reading feature status alone would infer the inference subsystem is unbuilt and might regenerate it. Status that never updates stops being information, and the compiler has all the data it needs to detect the staleness (behaviors linked via features [...] all carrying passing verifies). The fix is both a data correction and a coverage-driven diagnostic.

The to-do list still says 'maybe we'll build this' about things that are already built, shipped, and have tests. Nobody reading the list would know the work is done. Status that never updates stops being information.

Proposed solution. Promote the infer features to accepted/implemented status, and add a coverage-driven diagnostic: a feature whose behaviors all have passing linked tests but whose status is proposed should emit a warning.
