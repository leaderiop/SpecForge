CLI surface accretes: 28 top-level commands plus 17 product subcommands duplicate query/stats capability

mediumC2-04
005 Niklaus Wirtheffort Lmoves: CLI command surface
Evidencecrates/specforge-cli/src/main.rs:39-595 — Commands enum: 28 variants; ProductAction alone has 17 narrow list/analysis subcommands (features, journeys, ..., persona-features, channel-features, bulk-status, health)docs/entity-model.md:Extension CLI — docs present a compact 7-command mental model (init/add/remove/plugins...), diverging from actual 48-command surface

crates/specforge-cli/src/main.rs declares 28 top-level Commands variants, and the product surface alone contributes 17 narrow subcommands (features, journeys, persona-features, channel-features, bulk-status, health, …) that are all variations of show-me-product-graph-data. Meanwhile docs/entity-model.md Extension CLI presents a compact 7-command mental model, so documented and actual surfaces have fully diverged. This is classic CLI accretion — every analysis need became a new verb instead of an argument. Collapse the analytics under a single specforge query with domain/kind/op arguments, keeping only the documented 7 as top-level; completions and specforge explain survive. Large breaking change, needs a deprecation cycle.

Lean core is genuinely lean: 4 structural grammar rules, everything else generic — keep it that way

infoC2-09
005 Niklaus Wirtheffort Smoves: format versions supported
Evidencecrates/tree-sitter-specforge/grammar.js:1-12,68-77 — header states the design principle; only use/spec/ref/define have dedicated rules; entity_block parses ANY keyword; conflicts: [] — zero declared conflicts

The grammar keeps its founding promise: exactly four dedicated rules (use, spec, ref, define), everything else flowing through generic entity_block, and conflicts declared as an empty list — zero grammar conflicts in crates/tree-sitter-specforge/grammar.js. Adding a new domain kind requires zero compiler changes, the Project-Oberon-like property that makes the extension model viable at all. This is precisely the architectural invariant that erodes one just-this-once special case at a time, so it deserves a guard test: assert no domain keyword gains a dedicated rule without a recorded ADR. Effort is trivial; the protection is permanent.

// Guard for the zero-domain-core design principle (grammar.js header).
#[test]
fn core_grammar_has_no_domain_rules() {
    let src = std::fs::read_to_string("grammar.js").unwrap();
    let dedicated: Vec<&str> = src
        .lines()
        .filter(|l| l.trim_start().starts_with("//   - "))
        .map(|l| l.trim().trim_start_matches("// - "))
        .collect();
    // The four structural constructs, per the header ADR:
    let allowed = ["use", "spec", "ref", "define"];
    for name in &dedicated {
        assert!(
            allowed.contains(name),
            "dedicated grammar rule for '{name}' requires an ADR; \\
             domain keywords must stay on entity_block"
        );
    }
    assert!(src.contains("conflicts: ($) => []"), "conflicts must stay empty");
}
