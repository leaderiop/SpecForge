Auditor review

The router is refreshingly small - one match, thin handlers, no middleware zoo - which makes the two protocol sins stand out: answering a notification is the one thing JSON-RPC never forgives, and -32600 for pre-init is a lifecycle bug strict clients will catch in CI. Fix route() to return Option<JsonRpcResponse>, add the -32002 gate, and echo the negotiated protocolVersion; that is an afternoon and the server becomes conformance-testable. Capabilities honestly reporting list_changed:false is good discipline - keep telling the truth even after you make it interesting.

Server answers notifications and misuses JSON-RPC error codes

highC9-00
065 David Soria Parraeffort Smoves: MCP notifications conformance

The router returns a JsonRpcResponse for the notification method notifications/initialized, which per JSON-RPC 2.0 must never produce a reply - a strict MCP client receiving a frame for a notification can treat it as protocol garbage or tear down the connection. There is also no pre-initialize gate: any method other than initialize succeeds before handshake (registry handlers do check is_initialized, but ping/tools/call fall through). When handlers do reject they use -32600 INVALID_REQUEST, whereas the MCP lifecycle spec mandates -32002 for requests received before initialization. Finally, handle_initialize hardcodes protocol_version 2025-03-26 instead of echoing the client's requested version when supported.

pub fn route(state: &mut McpState, method: &str, params: Value, id: Option<Value>) -> Option<JsonRpcResponse> {
    // Notifications never get a response frame (JSON-RPC 2.0 section 4.1)
    if method.starts_with("notifications/") {
        return None;
    }

    if !state.is_initialized() && method != "initialize" {
        // MCP lifecycle: -32002 until initialize completes
        return Some(JsonRpcResponse::error(id, error_codes::SERVER_NOT_INITIALIZED, format!("Request before initialize: {}", method)));
    }

    let resp = match method {
        "initialize" => crate::lifecycle::handle_initialize(state, params, id),
        "shutdown" => crate::lifecycle::handle_shutdown(state, id),
        "ping" => JsonRpcResponse::success(id, serde_json::json!({})),
        "tools/list" => crate::registry::handle_list_tools(state, id),
        "resources/list" => crate::registry::handle_list_resources(state, id),
        "prompts/list" => crate::registry::handle_list_prompts(state, id),
        "resources/read" => crate::resources::handle_resource_read(state, params, id),
        "tools/call" => crate::tools::handle_tool_call(state, params, id),
        "prompts/get" => crate::prompts::handle_prompt_get(state, params, id),
        "$/cancelRequest" => crate::lifecycle::handle_cancel(state, params, id),
        _ => JsonRpcResponse::error(id, error_codes::METHOD_NOT_FOUND, format!("Method not found: {}", method)),
    };
    Some(resp)
}

Explain like I'm 10

A notification is like a postcard that says 'no reply needed' — this server writes back anyway, and strict clients will treat the unexpected reply as garbage or drop the connection. It also shouts 'wrong request' (a mail-format complaint) when the real problem is 'we have not been introduced yet' — two different mistakes, one shared label. Well-behaved MCP clients notice these things.

Proposed solution. Return None (no frame) for notification methods in route(); add a pre-initialize error path (code -32002 per MCP lifecycle); echo the client's requested protocolVersion when supported; move tool/resource/prompt listings behind the standard capabilities (tools.listChanged etc.) or document them as proprietary extensions.
