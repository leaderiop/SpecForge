But three of the four memory slots are a single giant page - context/graph/brief resources emit the whole corpus, which on your own ~1,245-entity spec means every resources/read is an L3 dump. The context resource handler emits the entire graph with no scope, depth, kind filter, or token budget - the signature is read(state, id) with no params, so even a client that wants 2% of the graph must pull ~1,245 entities into its window on this repo alone. brief.rs and graph.rs resources mirror this all-or-nothing shape, and there is no specforge://context/{entity_id} template, so the L1/L2/L3 paging ladder the README advertises exists at tool level (specforge.query --depth) but not at resource level. MCP resource URI templates support query components, so entity/depth/kinds/max_tokens params are protocol-legal. Until then, an agent that prefers resources over tools has no memory hierarchy at all.

// resources/context.rs - query params per MCP URI templates
pub fn read(state: &McpState, uri: &str, id: Option<Value>) -> JsonRpcResponse {
    let (base, query) = split_uri_query(uri);
    let mut options = EmitOptions { format: EmitFormat::Context, ..Default::default() };
    if let Some(root) = query.get("entity") {
        options.scope = Some(root);
        options.depth = query.get("depth").and_then(|v| v.parse().ok());
        options.token_budget = query.get("max_tokens").and_then(|v| v.parse().ok());
    }
    let json_str = emit(&state.graph, &options).expect("scoped emit cannot fail");
    JsonRpcResponse::success(id, serde_json::json!({
        "contents": [{ "uri": uri, "mimeType": "application/json", "text": json_str }]
    }))
}

Explain like I'm 10

The README sells RAM-and-paging for agents, but three of the 'memory' slots are a single giant page: on this repo's own spec (~1,245 entities), one resources/read loads everything into the model's window whether it needs 2% or 100%. There's no L1 (entity), L2 (subgraph), L3 (brief) handoff at the resource layer — even though query --depth already implements it one layer down.

Proposed solution. Accept optional query params on specforge://context|brief (root entity, depth, kinds, max_tokens) per MCP resource URI templates, and register specforge://context/{entity_id} so the multi-resolution ladder exists at resource level, not just tool level.
