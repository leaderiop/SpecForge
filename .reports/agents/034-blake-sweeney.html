HashMap storage patched with sort-at-every-read for determinism; removal is O(V+E) rebuild

Nodes live in HashMap so every ordered accessor sorts at read time (O(V log V) churn per call), remove_node rebuilds all indexes O(V+E), and neighbors allocate a fresh Vec per call. Switch to IndexMap for structural determinism and have neighbors borrow the index instead of copying.

use indexmap::IndexMap;

impl Graph {
    pub fn new() -> Self {
        Self {
            // Insertion-ordered: iteration is deterministic without the
            // sort_by_key on every read that HashMap forced.
            nodes: IndexMap::new(),
            edges: Vec::new(),
            source_index: HashMap::new(),
            target_index: HashMap::new(),
            bidirectional_pairs: HashSet::new(),
        }
    }

    pub fn nodes(&self) -> Vec<&Node> {
        self.nodes.values().collect() // O(V) borrow, no sort
    }

    /// Neighbors borrow the index instead of copying a Vec per call.
    fn neighbors(&self, id: Sym) -> impl Iterator<Item = Sym> + '_ {
        self.source_index.get(&id).into_iter().flatten()
            .map(|&i| self.edges[i].target)
            .chain(self.target_index.get(&id).into_iter().flatten()
                .map(|&i| self.edges[i].source))
    }

Explain like I'm 10

Imagine a phone book whose pages shuffle every time you open it, so you alphabetize the whole book before each lookup. An order-preserving book (indexmap-style) makes the sorting unnecessary, and neighbors could lend slices instead of copying lists.

Proposed solution. Switch nodes to indexmap::IndexMap (deterministic order, O(1) reads without sort) and have neighbors yield an iterator/borrowed slice; acceptable to keep edge-vec rebuild for removal at current scale, or adopt petgraph::StableGraph per the petgraph decision.
