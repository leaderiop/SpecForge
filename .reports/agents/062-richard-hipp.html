Auditor review

The schema is refreshingly boring in the right way: WAL, foreign keys, a UNIQUE arbiter ready for races, hashed tokens, yank as a flag. What worries me is one Mutex<Connection> hammered from async handlers with unwraps in prepare and query_map — one panic poisons the lock and every later request dies. Give me busy_timeout beside WAL, spawn_blocking or a pool, Result propagation, and a crash-reopen test.

Sync rusqlite behind a single Mutex called from async handlers blocks the Tokio runtime; several query paths .unwrap() into panics

mediumC8-08
062 D. Richard Hippeffort Mmoves: server_concurrency_safety

Database wraps one rusqlite Connection in a std Mutex with lock-unwrap in every method, called from async axum handlers: sync I/O stalls Tokio workers, a panic poisons the lock, and prepare/query_map unwraps turn I/O errors into connection resets; WAL is set without busy_timeout and there is no crash-reopen test. Move to spawn_blocking or a pool and propagate Results.

    pub fn open(path: &Path) -> Result<Self, String> {
        let conn = Connection::open(path).map_err(|e| e.to_string())?;
        conn.busy_timeout(Duration::from_millis(500)).map_err(|e| e.to_string())?;
        conn.execute_batch("PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;")
            .map_err(|e| e.to_string())?;
        Ok(Self { conn: Arc::new(Mutex::new(conn)) })
    }

    pub async fn with_conn<T, F>(&self, f: F) -> Result<T, String>
    where F: FnOnce(&Connection) -> Result<T, rusqlite::Error> + Send + 'static, T: Send + 'static {
        let conn = Arc::clone(&self.conn);

Explain like I'm 10

One kitchen key shared by every waiter means orders pile up while they wait; and a couple of recipes say 'assume the pantry is fine' — one missing ingredient explodes the whole kitchen instead of serving a sorry-we're-out dish.

Proposed solution. Connection pool or spawn_blocking, busy_timeout alongside WAL, propagate rusqlite errors as Result->500; add a crash/reopen WAL test.
